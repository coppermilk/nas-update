# nas-update

Безопасные автообновления docker-приложений на Synology NAS. Одна задача в
Task Scheduler запускается каждые 5 минут, а что и когда обновлять, решают
короткие конфиги в `apps/`.

Есть два вида приложений:

- **`source = git`**: код из репозитория, куда пушат ИИ-агенты или CI. Он
  **недоверенный**: агент может закоммитить что угодно, а обновление идёт
  от root.
- **`source = releases`**: стороннее приложение с релизами на GitHub
  (например Immich). Издателю доверяем, но новая версия может что-то
  сломать.

## Модель угроз и что гарантируется

Root исполняет только код из этой папки. Всё, что приходит из репозитория
приложения, для nas-update — данные, и они проверяются до того, как
попадут в Docker.

| угроза | защита |
|---|---|
| вредный скрипт в репо (`deploy.sh` и т.п.) | из репо ничего не исполняется; git без хуков и fsmonitor |
| compose монтирует `/`, `docker.sock`, чужие папки | bind только внутри `data` (запись) и `readonly` (чтение) |
| `privileged`, `cap_add`, устройства, host-сеть, `pid`/`ipc`, sysctls, `group_add`… | запрещены; неизвестный ключ compose — тоже запрет |
| `env_file`/`include`/`extends` читают файлы хоста (пароли других приложений) | compose рендерится **в chroot**, где есть только коммит и `.env`: чужих файлов там физически нет |
| проверили одно, запустили другое | деплоится ровно проверенный JSON |
| контейнер от root читает личные файлы | контейнеры главного образа — от отдельного пользователя DSM (`run_as`), его права задают ACL |
| подмена чужого тома или сети (БД соседнего приложения) | только свои тома и сети проекта, без `external` и `driver_opts` |
| симлинк, подложенный в данные | путь bind не может идти через симлинк |
| коммит затирает `.env` или сессии | защищённые файлы в коммите = блок |
| новая версия упала | проверка здоровья, автоматический откат на прежние коммит, образ и JSON |
| обновление испортило данные | без свежего снапшота шары с данными обновления нет |

Секреты в этот репозиторий не попадают: `.env` лежат в папках приложений,
настройки — в `apps/*.conf` на NAS (`.gitignore`). Безопасность не держится
на секретности кода.

**Обновление самого nas-update** — единственное, что может дать root на
NAS, поэтому:

- NAS никогда не обновляет nas-update сам; ты ставишь конкретный коммит
  вручную;
- писать в этот репозиторий может только владелец (агентам доступа нет);
- тесты гоняются в CI на каждый пуш.

## source = git

Каждый запуск (`schedule = always`):

1. `git fetch`. Коммит деплоится только с образом из реестра, собранным из
   него же (метка `org.opencontainers.image.revision`).
2. Дерево коммита: только обычные файлы, без симлинков и сабмодулей; файлы
   из `protected` не коммитятся; git не затрёт локальные файлы.
3. `compose config` в chroot, затем политика (таблица выше). В тот же JSON
   дописываются `user: run_as` и `no-new-privileges`.
4. Свежий снапшот шары с `data`. Проверка доступа `run_as` ко всему, куда
   он может писать. Файлам root в «Linux mode» (это бывает, когда контейнер
   сделал им `chmod`) возвращается наследование ACL от папки.
5. `down`/`up`. Если контейнеры не проживут `verify_sec` без перезапусков,
   идёт откат.

Первый запуск принимает текущий чекаут и образ за работающие и стек не
трогает.

## source = releases

Раз в день в окне `schedule = HH:MM-HH:MM`:

1. Отслеживается major из `.env` приложения (`IMMICH_VERSION=v3`).
2. Ставится самый новый стабильный релиз этого major, которому уже
   `cooldown_days`. Свежий x.y.0 часто чинят на следующий день.
3. Если в заметках к релизу есть «breaking» или в эталонном compose из
   релиза другой образ из `stop_if_image` (база), nas-update ничего не
   ставит и присылает письмо.
4. Нужен свежий снапшот шары с приложением.
5. `pull` и `up -d` ровно этой версии; `.env` не меняется. Ждём, пока всё
   станет healthy и сервер ответит новой версией (`version_url`).
6. Если не поднялось, возвращается прежняя версия из локальной копии
   образа. Если поднялось, старые образы удаляются.

Про новый major приходит одно письмо. Переходишь на него сам.

## Установка и обновление на Synology

Нужны DSM 7 (там есть python3 3.8 и git) и Container Manager. Docker
compose 2.29.7 nas-update скачивает сам и сверяет по sha256.

1. Папка — `/volume1/docker/nas-update/`: вне репозиториев приложений и вне
   папок, которые видят контейнеры (nas-update это проверяет). Положи в
   `apps/<имя>.conf` конфиги по примерам из `examples/`.
2. Snapshot Replication: снапшоты шар с данными чаще, чем
   `snapshot_max_age` (например, homes — каждый час).
3. Task Scheduler → Create → Scheduled Task → User-defined script, от root,
   **без расписания** (запускаешь руками), «nas-update install». `C` —
   полный sha коммита, который ты прочитал:
   ```sh
   D=/volume1/docker/nas-update
   C=0123456789abcdef0123456789abcdef01234567
   mkdir -p $D/apps && cd $D || exit 2
   [ -d .git ] || git init -q
   git fetch -q --depth 1 https://github.com/coppermilk/nas-update $C || exit 2
   git checkout -qf --detach $C || exit 2
   git rev-parse HEAD
   sh $D/nas-update.sh --dry-run
   ```
   Запусти и посмотри вывод: какой коммит стоит и что nas-update сделал бы.
   **Обновление** nas-update — та же задача с новым `C`, после того как
   прочитал diff. `apps/` и `state/` git не трогает.
4. Вторая задача — от root, каждые 5 минут:
   `sh /volume1/docker/nas-update/nas-update.sh`.
   Включи письмо «only when the script terminates abnormally».

## Письма и коды выхода

| код | что значит |
|---|---|
| 0 | готово, нечего делать или ждём |
| 2 | ошибка (конфиг, сеть, git) |
| 3 | нужно твоё решение: заблокировано, отложено, нет снапшота, вышел новый major |
| 4 | новая версия упала, откат удался |
| 5 | откат тоже не поднялся |

Если приложений несколько, код — худший из них. Об одной проблеме
приходит одно письмо. Отклонённую версию nas-update не трогает, пока не
появится новая версия или не изменится nas-update или конфиг приложения.
Временные сбои напоминают о себе раз в 6 часов.

## Файлы

| | |
|---|---|
| `nas-update.py` | точка входа: приложения, расписание, блокировка, коды |
| `core.py` | общее: журнал, письма, compose, снапшоты, здоровье, чистка образов |
| `git_source.py` | `source = git`: клетка, политика, `run_as`, доступ к данным |
| `release_source.py` | `source = releases`: релизы GitHub, задержка, стоп-сигналы |
| `apps/*.conf` | твои приложения (локально, не в git) |
| `state/` | журнал `update.log` и состояние приложений (локально) |

## Тесты

От root (нужны chroot и смена пользователя), с закреплённым compose:

```sh
export COMPOSE_BIN=/path/to/docker-compose-2.29.7
sudo -E python3 tests/test_policy.py    # политика на «злых» compose
sudo -E python3 tests/sim_git.py        # симуляция NAS для source=git
sudo -E python3 tests/sim_releases.py   # симуляция NAS для source=releases
```
